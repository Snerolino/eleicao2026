# 4. Metodologia do dossiê

## 4.1 Três camadas independentes

### Fato

```text
proposição
→ versão
→ evento de votação
→ voto nominal
→ presença/ausência
→ fonte
```

### Avaliação

```text
grupo afetado
→ direção do impacto
→ defending_vote
→ severidade
→ tipo estrutural
→ confiança
→ rationale
```

### Derivação

```text
voto + assessment
→ alinhamento
→ peso
→ score por grupo
```

Uma mudança na metodologia não reescreve o voto original.

| `nao_avaliavel` | excluído |

## 4.4 Regra de votos procedimentais

Voto de:

- urgência;
- retirada de pauta;
- adiamento;
- encerramento de discussão;
- quebra de interstício;

é registrado como fato, mas **não é automaticamente tratado como voto substantivo no mérito**.

Exemplo:

```text
Sim à urgência de um projeto
≠
Sim ao conteúdo final do projeto
```

Essa distinção é especialmente importante para reconstruir uma carreira longa sem fabricar posições que o painel nominal não registra.

---

## 4.5 Regra para sequências complexas

Uma mesma matéria pode produzir:

```text
Não ao substitutivo
Sim a uma emenda
Sim à redação final
```

Não é legítimo reduzir isso a:

```text
“votou Sim”
```

sem indicar qual versão e qual objeto.

A MPV 1031/2021, sobre a Eletrobras, é um caso concreto neste dossiê.

# 15. Melhorias metodológicas descobertas neste dossiê

## 15.1 `policy_topics` deve existir separado de `beneficiary_groups`

Exemplo:

```yaml
proposition: PLP 19/2019
policy_topics:
  - bancos
  - politica_monetaria
beneficiary_groups: []
```

É melhor do que inventar `geral`.

---

## 15.2 Voto procedimental precisa de flag

Recomendação:

```yaml
vote_scope:
  substantive
  procedural
  drafting
  amendment
  secret
```

Isso impediria que:

```text
urgência = apoio ao mérito
```

por acidente.

---

## 15.3 Redação final não deve substituir voto de mérito anterior

A MPV 1031/2021 prova que:

```text
substitutivo = Não
redação final = Sim
```

pode ocorrer na mesma matéria.

O banco precisa manter ambos.

---

## 15.4 Coverage deve acompanhar todo score

Nunca mostrar:

```text
mulheres: -1.00
```

isoladamente.

Mostrar:

```yaml
score: -1.00
evaluated_score_units: 1
career_coverage: insufficient
publication_ready: false
```

# 19. Regra de uso deste arquivo

Este dossiê pode ser usado como:

- referência humana;
- seed para pipeline de pesquisa;
- base para gerar fixtures;
- fonte de candidatos a assessments;
- exemplo para padronizar outros candidatos;
- material para revisão metodológica.

Mas os campos abaixo continuam sendo **interpretação derivada**:

```text
beneficiary_group
severity
structural_type
impact_direction
defending_vote
confidence
alignment
score
policy_topics
```

Os campos factuais devem sempre preservar fonte:

```text
proposition_id
version/object
vote
date
attendance
absence_reason
source
```

## Princípio final de auditoria

Qualquer resultado deve poder ser percorrido ao contrário:

```text
score
↓
alignment
↓
assessment
↓
voto
↓
versão da proposição
↓
evento de votação
↓
fonte oficial
```

Se uma conclusão não puder fazer esse caminho, ela não deve entrar como dado confiável.
